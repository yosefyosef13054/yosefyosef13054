### Technical Philosophy

<details>
<summary><b>How I think about building software</b></summary>

<br/>

- **Production over demo.** A working pipeline beats a slick prototype. Auth, rate limits, cost tracking, and observability are part of v1, not v2.
- **Streaming is UX.** For LLM products, the difference between "feels fast" and "feels broken" is whether tokens arrive incrementally. The backend, the transport, and the client all have to cooperate.
- **Memory and retrieval are the product.** Anyone can call an LLM. The hard part — and the part users actually feel — is what context you put in the prompt and how you measure whether retrieval is good.
- **Integration-ready by default.** I'd rather build a clean module that drops into someone else's stack than another standalone "AI app." That's where the real leverage is.
- **Mobile shipped beats web prototyped.** Two app-store releases teach you more about edge cases than ten side projects.

</details>

<details>
<summary><b>Architecture interests</b></summary>

<br/>

- API-first systems with **typed contracts** (Pydantic / OpenAPI) and generated clients.
- **Async-everything** backends — SQLAlchemy 2 async, FastAPI, background workers via Celery.
- **Vector + relational** data living in the same Postgres instance via pgvector — fewer moving parts, fewer bugs.
- **SSE over WebSocket** when one-way streaming is enough; reserving WebSocket for true bidirectional state.
- **Riverpod**-shaped Flutter state — provider composition over global singletons, testable units.

</details>

<details>
<summary><b>Open-source goals</b></summary>

<br/>

- Publish **NEXUSBOT** as a credible reference for "what a production LLM backend actually looks like."
- Release the **Flutter streaming-chat client** as a reusable package — SSE + tool calls + RAG, batteries included.
- Open-source the **AI Meeting Assistant** Laravel module once it's stable.

</details>
